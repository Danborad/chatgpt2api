# 工作流规则

## 任务状态机

每个非简单修改依次经过以下阶段：

1. **检查**：查看 Git 状态、相关代码、测试、当前文档和运行状态。
2. **分析**：说明事实、问题根因、范围、风险以及不做什么。
3. **计划**：建立当前任务的短期步骤；不要复用过期计划，不把计划写成完成事实。
4. **同步与确认**：在编辑前先用自己的话复述需求、将修改的 Module、Interface 或行为以及验证方式；等待用户确认范围后才能写入。
5. **实现**：小批量、就地修改；每完成一组就更新计划状态。
6. **验证**：按风险运行针对性测试，再运行需要的完整回归和界面检查。
7. **汇报**：说明结果、改动文件、验证范围、未验证项和 Git 状态。

简单的一处文案或明确机械修改可以缩短计划，但仍须先检查相关文件并在编辑前说明。

## 状态边界

- **计划中**：只表示准备执行，不是已经发生的事实；除非用户明确要求，不创建长期计划文件。
- **已实现**：目标代码已经修改，但必须另外说明自动测试、浏览器检查和未验证项，不能据此声称用户已验收。
- **已验收**：只有用户明确确认可见行为符合要求时才成立，不能由测试通过、构建成功或 Agent 自查推断。
- **已发布**：只有对应的 push、tag、Release、镜像或 npm 发布动作实际成功后才成立；本地提交和未推送 tag 不属于已发布。

不同状态不得互相替代。汇报时使用当前真实状态，不用“完成”“没问题”等笼统表述掩盖尚未验证、尚未验收或尚未发布的部分。

## 请求类型

- “Review、检查、分析、解释、给建议”只授权只读操作，不得顺手修复。
- “修复、优化、开始、实现”授权在已确认范围内写入，但不自动授权提交、推送、发布或扩大架构范围。
- “提交”只授权当前仓库的本地提交；是否包含另一个仓库必须单独说明。
- “推送、发布、打包、重跑 CI 或 Workflow”分别是独立远程动作；执行前必须逐项获得用户明确授权，不能互相推断授权。

用户打断时先判断新消息是补充还是替换。若只是补充，完成正在进行的安全步骤后纳入当前任务；若明确要求停止，立即停止写入并汇报已发生的修改。

## 范围和工作区

- 编辑前检查目标文件当前差异，确保不会覆盖用户修改。
- 生产代码引用的未跟踪文件必须纳入完整性检查，不能只看已跟踪差异。
- 临时测试目录、日志、构建产物、备份和真实数据不得混入源码提交。
- 备份文件按敏感用户数据处理。除非用户明确要求，不读取内容、不删除、不提交。
- 遇到需要新授权、数据迁移、公开接口破坏或跨仓库发布时停在相应门槛前说明。

## 纠正沉淀

- 用户纠正后先判断是当前任务偏好还是长期约束；具有长期价值的要求在当前任务内写入最相关规则。
- 新增规则前先搜索现有规则、文档和脚本。已有同义规则时修改原条目，不追加另一套表达。
- 规则必须写明触发条件、必须执行的动作和禁止结果，不能只记录“注意统一”“避免混乱”等无法检查的愿望。
- 规则与代码、脚本、`.gitignore` 或实际 Git 跟踪状态冲突时，不能声称规则已经落地；应修正规则或在获得相应授权后修正仓库状态。

## 任务完成门禁

最终汇报前逐项确认：

1. 实际差异仍在用户授权范围内，没有顺手修改或覆盖用户已有内容。
2. `git status --short`、相关 `git diff` 和未跟踪文件均已检查；跨仓库任务分别检查每个仓库。
3. 已按风险完成必要验证，并明确区分自动测试、浏览器检查、用户验收和未验证项。
4. 用户可感知行为、Interface 或路由变化已检查 `CHANGELOG.md` 和 current 文档是否需要同步；计划内容没有被写成完成事实。
5. 当前任务计划状态已更新，仍未完成的步骤、阻塞条件和所需新授权已明确说明。
6. 最终汇报包含实际结果、验证证据、Git 状态，以及另一个相关仓库是否存在未提交或未推送内容。

任一必需项未完成时，不得声称任务“已完成”或“没有问题”；应准确说明当前停在哪个状态。

## 最小实现阶梯

完成必要检查并理解真实调用链后，按顺序选择第一个可以完整满足需求的方案：

1. **不新增**：先做删除测试；现有行为已经满足需求时，不增加代码、配置或文档事实。
2. **复用现有所有者**：优先扩展已有 Module、Interface、组件或辅助函数，不复制第二套实现。
3. **使用平台能力**：优先使用标准库、框架和浏览器原生能力。
4. **使用已有依赖**：已安装且适合的成熟依赖能够解决时，不手写同类基础能力，也不再引入替代依赖。
5. **就地最小修改**：前述方案不成立时，在当前所有权边界内完成小而明确的实现。
6. **新增抽象或依赖**：只有能够证明前述方案不足，并且确实减少复杂度、真实重复或跨项目维护成本时才允许新增。

- 该阶梯在读懂相关代码、契约和所有权之后使用，不能代替检查与分析。
- “最小”指满足完整行为的最小方案，不得删减输入校验、错误处理、安全边界、事务完整性、可访问性、取消与清理逻辑。
- 新增 Module、依赖、配置项、状态、存储结构或兼容分支前，必须能说明前一层为何不足；不能新增只改名、只转发参数或只包一层的浅 Module。
- 页面私有逻辑保持 Locality；只有真实重复或明确跨项目复用时才提炼。
- 标准格式、协议、URL、JSON、日期和安全校验优先使用结构化接口或成熟库。
- 修改聚焦根因；不要用额外 CSS、兼容分支或重复状态掩盖生命周期和数据问题。
